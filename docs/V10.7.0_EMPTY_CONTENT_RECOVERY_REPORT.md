# SoloHost Browser V10.7.0 — Empty-content and recursive viewport recovery

## Log diagnosis

The log repeatedly showed URLs of the form `/api/browser/sessions/:id/view?token=...` being passed back to `client.navigate` and `proxy.request`. These URLs are the app's own sanitized iframe viewport, not a website. The frame `load` listener copied `frame.contentWindow.location.href` into `state.url` without excluding the internal bridge view. The next reload or agent action therefore navigated the app back into its own viewport endpoint, causing recursive fetches and white pages.

A second bug made this harder to detect: `sanitizeHtml('')` appended bridge CSS, so an empty response became a non-empty string and `hasContent` could be true despite no renderable page content.

## Changes

1. `public/app.js`: added `isInternalBridgeViewUrl`; do not overwrite the actual site URL when the iframe loads the internal view; block attempts to navigate to that internal view and restore the real URL in the address bar.
2. `server.js`: reject same-host session `view/state/content/navigate/events` endpoints as navigation targets with `internal_url_not_navigable`. This avoids recursive self-fetching even if a client/agent submits such a URL.
3. `lib/engine/dom-bridge.js`: `sanitizeHtml` leaves empty/CSS-only documents empty; `hasRenderableContent` checks actual text/media/controls and worker audit; public `hasContent` uses meaningful-content detection.
4. Clear the prior page's HTML/map/audit/title before a new navigation so failures cannot expose stale content.
5. If WebKit or Proxy returns an empty snapshot, log `bridge.empty_content` and return a recoverable failure instead of claiming success. Client fallback can then use the normal proxy path.
6. Added regression tests for empty HTML, CSS-only HTML, media-only pages, internal viewport guards, and server route protection.

## Preserved

No UI redesign. Chat, Feedback, Settings, Logs, tabs, history/bookmarks, AI modules, feedback module, SoloHost packaging, Node/Express, SSRF policy, session-token checks, and external-open behavior remain in place.
