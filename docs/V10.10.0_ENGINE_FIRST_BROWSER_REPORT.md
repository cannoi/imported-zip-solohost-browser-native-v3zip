# SoloHost Browser 10.10.0 — Engine-first browser backend report

## Problem analysis

The app is not a conventional visible browser window: Playwright executes the live page, but the UI displays a sanitized DOM snapshot in a same-origin iframe. That protects the app shell from remote page scripts, but it cannot reproduce every interaction, cross-origin iframe, canvas, service-worker, media, or highly dynamic SPA exactly. The previous YouTube fallback also scanned all watch links on the page and could replace the home/feed with embed cards. Dynamic pages could wait up to eight seconds for `networkidle`, despite long-lived requests.

Google documents that sign-in can be blocked in browsers controlled by automation or embedded inside another application, and recommends a supported system browser for these authentication flows. The app therefore must not try to evade that decision.

## Changes in 10.10.0

- Persistent Playwright storage state is enabled by default for the local app profile. Cookies and local storage are saved to `/app/data/browser-state`, with a hashed profile filename, directory mode `0700`, file mode `0600`, and atomic writes. Set `SOLOHOST_BROWSER_PERSIST_SESSIONS=0` to disable persistence.
- Storage is saved after navigation, click/submit, and session close. A fresh context's current state is authoritative; stale cookies are not intentionally merged back after sign-out.
- Popups opened by the page are tracked as the active page. Recovery reattaches popup tracking.
- Navigation no longer waits for `networkidle`; it uses `domcontentloaded` plus a short settle period.
- YouTube feed/home pages are no longer turned into embed-card pages merely because their DOM contains video links. Embed fallback IDs are derived only from a specific `/watch?v=...` or `youtu.be/<id>` URL and are used only when the page is too thin to render.
- Google Accounts and known Facebook/TikTok login routes are directed to the system browser. Redirects into those routes produce a clear external-browser handoff rather than trying to keep the sign-in inside the controlled frame.
- Capabilities and SoloHost Compose environment metadata are updated to 10.10.0.

## Compatibility and security boundaries

- Ordinary Google search and YouTube pages still use the engine-first route. Known authentication endpoints use the system browser.
- System-browser cookies are not copied into the embedded engine. This is intentional; silently extracting or sharing credentials across browser contexts would be unsafe and would not comply with provider auth policies.
- The app does not bypass CAPTCHA, anti-bot challenges, account verification, rate limits, DRM, or website access controls.
- The UI remains a sanitized DOM Bridge, not a pixel-perfect live Chromium surface. Canvas-heavy sites, protected cross-origin frames, DRM, and some media playback may still require the system browser.
- Persistent state includes authentication cookies/local storage. Users can disable it with `SOLOHOST_BROWSER_PERSIST_SESSIONS=0` or remove files from `/app/data/browser-state` to clear saved site sessions.

## Validation

- `node --check` is run for all JavaScript files.
- `npm test` covers existing UI/backend/security/SSRF/AI/agent/YouTube/Bing regressions plus new browser standards tests.
- Compose/config YAML is parsed before packaging.
- ZIP archive is tested for integrity and inspected for required project files.
- A live SoloHost deployment, provider sign-in, and video playback cannot be asserted from static tests; these require testing in the target SoloHost runtime.
