# SoloHost Browser V10.6.0 — JavaScript and IPC Recovery Report

## Scope and compatibility

This patch is additive and targets the failures in the 2026-10-11 logs. It preserves the existing UI, Chat, Feedback, Settings, Logs, history/bookmarks, SoloHost package format, Node/Express server, SSRF checks, proxy fallback, and external-open policy. No VNC/noVNC or new browser UI was added.

## Diagnosis

1. Google showed its JavaScript-disabled interstitial. The WebKit worker relied on default WebKit settings rather than explicitly enabling JavaScript. The live page can run scripts, but exported snapshots intentionally omit scripts because the viewport is sanitized HTML.
2. The Python worker processes JSON-lines requests synchronously. Node previously wrote concurrent commands to stdin and started each IPC timeout immediately. Commands queued behind a slow navigation could therefore time out before Python had started handling them; subsequent responses could become stale or unmatched.
3. Any WebKit navigation error downgraded the session to proxy and imposed a ten-minute cooldown, making one failure affect later pages.
4. Repeated requests for the same URL could overlap while the worker was busy.
5. App-log redaction attempted to modify serialized JSON text; when a secret appeared inside a URL string, inserted quotes could make parsing fail and return the original unredacted object.

## Changes made

- Explicitly set WebKit's `enable-javascript` setting on every created WebView; the page continues to execute scripts in its live document. The snapshot still removes script tags only from a cloned DOM for safe rendering.
- Introduced a single-flight IPC queue. Only the active command has a running timeout; queued commands do not time out while waiting. If an active command really times out, the worker is terminated and stale queued commands are rejected rather than contaminating later requests.
- Guarded worker exit handling so a delayed exit event from an old process cannot clear the reference to a replacement worker.
- Coalesced identical in-flight navigations and serialized different navigations for each browser session.
- Changed cooldown behavior: 45 seconds for worker/IPC faults, 5 seconds for page-level failures. A later navigation can recreate a WebKit session and recover from temporary proxy fallback.
- Reworked log redaction as recursive value sanitization, including URL query parameters such as `token=`, `access_token=`, `refresh_token=`, `api_key=`, and credential fields. Added a regression test.
- Added assertions for JavaScript enablement, IPC serialization and navigation coalescing.

## Remaining limitations

This app still exports a sanitized DOM snapshot plus an event bridge; it is not a full pixel-native browser surface. Explicitly enabling JavaScript in WebKit does not guarantee that Google, YouTube, TikTok, or every login/SPA flow will accept WebKitGTK or that the snapshot can represent every dynamic component. CAPTCHA, anti-bot checks, DRM, file upload and some cross-origin iframe behavior may still require opening the page in a full external browser.

Previously written log files may contain tokens emitted before this release. Clear old logs and rotate/expire affected browser sessions; the new redaction only protects newly written logs.

## Rollback

Restore the previous ZIP/image if this build behaves worse in SoloHost. Set `SOLOHOST_WEBKIT_BRIDGE=0` to force proxy-only bridge behavior or `SOLOHOST_WEBKIT_PERSIST_COOKIES=0` to disable persistent cookie storage.
