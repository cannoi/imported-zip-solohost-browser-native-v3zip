# SoloHost Browser v10.24.0 — noVNC Interactive Chromium Report

## Implemented

- Added an opt-in Xvfb + Openbox + x11vnc + noVNC/websockify desktop runtime to the Docker image.
- Added `SOLOHOST_NOVNC_ENABLED` and `NOVNC_VNC_PASSWORD` configuration options. The desktop will not start unless explicitly enabled and a password of at least 8 characters is set. The classic VNC protocol effectively uses only the first 8 characters, so this should be treated as a dedicated VNC password, not reused elsewhere.
- x11vnc binds to loopback only; websockify serves noVNC on port 6080 and forwards WebSocket traffic to the password-protected VNC server.
- Docker now starts through `start.sh`, which launches the desktop services before the app. Port 6080 is exposed and mapped in Compose.
- When noVNC is enabled, Playwright Chromium runs headed on the same X display, so pages/contexts opened by the existing Playwright engine can be observed and directly controlled through VNC. This preserves the existing browser engine/session management instead of starting an unrelated second Chromium instance.
- Added an app toolbar action and `/api/novnc/status` endpoint. The endpoint is covered by the app's existing access middleware and never returns a URL unless noVNC and its password are configured.
- Added English/Vietnamese status/error messages for the toolbar action.

## Configuration

Set in SoloHost configuration / environment:

```env
SOLOHOST_NOVNC_ENABLED=1
NOVNC_VNC_PASSWORD=use-a-unique-password-of-at-least-8-chars
SOLOHOST_BROWSER_HEADFUL=1
```

Restart/rebuild the container after changing Dockerfile or environment. Open the app and use the 🖥️ toolbar button. The noVNC endpoint is port 6080. The deployment platform/network must publish this port to the user; the app cannot make a host port reachable if SoloHost's ingress does not expose it. The VNC password prompt is separate from the browser app password.

When noVNC is disabled, `start.sh` forces headless Chromium to preserve existing low-resource behavior.

## Session relationship and limitations

- This implementation uses the same Playwright Chromium browser process and X display. It does not create an unrelated noVNC-only browser profile.
- VNC shows the shared X desktop. If multiple Playwright pages are open, Chromium may show multiple windows; selecting a window changes which page is visible. The app's DOM Bridge tab selection is not automatically synchronized with the active OS window, because the current engine does not have a one-to-one OS window focus contract.
- The browser app access password and VNC password are separate. Keep port 6080 private or behind a trusted TLS/reverse-proxy layer. Do not reuse the app password. Classic VNC password handling limits effective password length to 8 characters.
- CAPTCHA challenges may still be rejected by the website; noVNC only gives a human direct input/display path and does not bypass CAPTCHA or site security controls.
- A full live smoke test requires building/running the Docker image on a host with Docker and a browser-capable display. The current environment ran static/unit regression checks but did not launch a real VNC client against a running SoloHost container.
