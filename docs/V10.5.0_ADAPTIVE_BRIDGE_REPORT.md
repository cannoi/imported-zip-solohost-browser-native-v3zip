# SoloHost Browser V10.5.0 — Adaptive JavaScript and Login Bridge

## Scope

This upgrade keeps the existing Node/Express application, SoloHost package layout, UI, Chat, Feedback, Settings, Logs, history/bookmarks, SSRF controls, and external-open escape hatch. It does not introduce VNC/noVNC or change the viewport design.

## Findings from V10.4.1

1. `native/webkit-worker/worker.py` removed `<script>` elements from the *live WebKit DOM* while extracting page content. That can stop SPAs and other sites from continuing to run their own JavaScript. Extraction now clones the DOM and removes scripts only from the clone sent to the snapshot viewport.
2. The bridge forwarded clicks and form submits but not ordinary input/change events. Login fields, selects, checkboxes and radio buttons could not reliably synchronize with the live WebKit page. Input events are now forwarded; password values are not copied into HTML snapshots or diagnostics.
3. Bridge input events reloaded the iframe after every event and marked input as page loading, which could lose focus and make login entry appear stalled. Input/change no longer reloads the snapshot, and only navigation-like actions set loading state.
4. The old route policy selected proxy for Google and YouTube and external browser for many social/login pages, so the JavaScript-capable engine was bypassed. Dynamic sites and login paths now prefer WebKit Bridge; DRM-heavy streaming remains external and proxy remains fallback.
5. There was no source-vs-render quality signal. WebKit now returns structural metrics; the UI compares source and rendered counts, logs suspected content loss, and asks the existing AI compatibility helper for advisory findings when a snapshot is empty or materially incomplete.
6. The AI compatibility timeout race left a timer alive after early completion. The timer is now cleared in `finally`.

## Changes

- WebKit Bridge enabled by the shipped Dockerfile (`SOLOHOST_WEBKIT_BRIDGE=1`), with bounded 20s navigation and 30s IPC timeouts.
- WebKit DOM snapshot uses a clone, preserves live scripts and live page state, and reports text length, script count, forms, controls, media, iframes, links and readyState.
- Password inputs are sent only through the local app-to-worker event channel to update the live WebKit field. Passwords are omitted from the serialized snapshot. Diagnostics contain counts and compatibility metadata only.
- Cookie persistence is enabled by default in `/app/data/browser-profile/cookies.sqlite` to support login continuity across restarts. Set `SOLOHOST_WEBKIT_PERSIST_COOKIES=0` to disable it. Treat the app data volume as sensitive; do not share its cookie database.
- Bridge input handling covers text/password input, checkbox/radio state, select changes, submit and Enter-to-submit. File upload remains unsupported in the DOM snapshot bridge.
- Source/render audit and AI compatibility findings are written to the existing app log without sending page text, passwords, cookies or AI provider secrets.
- Existing YouTube-to-official-embed handling is preserved for direct video playback.
- Existing SSRF checks and HTML sanitization remain in place.

## Honest limitations

This is still a **DOM snapshot + event bridge**, not a native pixel-rendered browser surface. The website JavaScript executes inside WebKit, but the visible copy is sanitized HTML and needs the event bridge to keep interactions synchronized. Complex SPA components can still differ from the source page. CAPTCHA, anti-bot checks, DRM-protected streaming, file upload, some cross-origin iframe apps and sites that reject embedded WebViews may still require Open ↗. Persistent cookies improve login continuity but do not guarantee every provider will accept WebKitGTK as a browser.

## Rollback

- Set `SOLOHOST_WEBKIT_BRIDGE=0` to use proxy-only bridge sessions.
- Set `SOLOHOST_WEBKIT_PERSIST_COOKIES=0` to disable persistent cookies.
- Restore the previous ZIP/image if the updated engine behaves worse on the target SoloHost runtime.
