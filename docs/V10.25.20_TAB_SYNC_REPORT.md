# SoloHost Browser v10.25.20 — Bridge tab synchronization report

## Scope

Input: `solohost-browser-v10.25.19-tab-sync-cleanup.zip`.

This upgrade deliberately preserves the existing SoloHost application and changes only the Static Capture remnants, Chromium/Bridge session ownership, asynchronous tab rendering, link routing, version/AI capability metadata, and regression tests.

## Findings

### 1. Static Capture

The uploaded source did not contain a standalone `static-capture.html`, a Static Capture route, or a static crawler implementation. It did retain stale capability flags, an exported `createCapturePage()` helper, AI/README descriptions, and a dependency stack used only by the unused `extractReadable()` path. The Docker dependency smoke-check also required `archiver`, although it was not a package dependency.

Removed:

- Static Capture capability flags and its stale feature claim.
- The unused auxiliary `createCapturePage()` API and export.
- The unused `extractReadable()` implementation and its `@mozilla/readability` / `jsdom` dependencies.
- The incorrect `archiver` requirement in the Docker dependency smoke-check.
- Stale AI and README descriptions that advertised a separate Static Capture feature.

Kept:

- `content-pipeline.js` because the Bridge still uses live DOM inspection, metadata, page-family signals, and the interactive DOM snapshot pipeline.
- `sanitize-html` because the Bridge uses it to sanitize its display copy.

## Root causes addressed

### 2. Shared BrowserContext popup fan-out

The prior `attachPopupTracking()` subscribed every session to `context.on('page')`. All normal tabs share the same persistent BrowserContext/profile, so one popup was delivered to all session listeners. Each listener then navigated its own page to the popup URL, explaining why multiple backend Chromium tabs could converge on the same content.

Fix: popup handling is attached to the specific opener page (`page.on('popup')`). It only absorbs that popup into the opener's page, serializes popup navigation per session, and closes the auxiliary popup. Other tabs in the shared profile are not navigated by that popup handler.

### 3. Session recovery stole the first page in a shared profile

The prior recovery path selected `context.pages()[0]`. In a shared profile this page could already belong to a different SoloHost tab, causing two sessions to point at the same Chromium page.

Fix: `findUnownedPage()` searches for an unowned blank page first, then another unowned live page. Recovery excludes its own stale state and never steals a page currently owned by another session. New sessions use the same ownership helper. The profile page cap is explicit and returns `browser_page_limit_reached` instead of silently creating unbounded pages.

### 4. UI tab limit and backend session caps disagreed

The UI allows up to 12 tabs, but Playwright defaulted to 4 sessions and Bridge to 6. When the backend evicted an older session, its SoloHost tab could still retain stale session credentials.

Fix: Bridge and Playwright defaults now both align with the 12-tab UI and the default maximum page count is 12. Operators can lower `SOLOHOST_BRIDGE_MAX_SESSIONS`, `SOLOHOST_PW_MAX_SESSIONS`, and `SOLOHOST_MAX_PAGES` for memory-constrained deployments; for strict one-to-one tab behavior, these limits should be configured consistently. Twelve live Chromium pages can consume substantial RAM on a small Pi host.

### 5. Asynchronous tab-switch race

A navigation started in one tab could finish after the user switched tabs and then replace the shared iframe or update the active omnibox with the wrong tab's URL.

Fix: the iframe is tagged with `data-sh-tab-id`. Bridge navigation responses only render when their originating tab remains active. Late responses update the originating tab's cached URL/title without replacing the active viewport. Click/input/change/submit/Enter handlers ignore stale iframe events, and URL changes from bridge events are applied only to the originating active tab.

### 6. Link routing consistency

- Bridge and proxy links continue to route through SoloHost navigation rather than uncontrolled host-browser popups.
- Proxy-rendered `_blank` links preserve new-tab intent using `data-sh-open-new-tab`.
- `mailto:` and `tel:` links have an explicit parent-protocol handler.
- `javascript:`, `data:`, and `blob:` are not routed as website navigation.
- Relative links in the interactive Bridge snapshot resolve against the originating tab's URL rather than an unrelated active tab's URL.
- Legacy tests were updated where they asserted the older proxy-link contract or expected uncontrolled iframe popups. The current proxy contract normalizes links to absolute destinations and routes clicks through the injected SoloHost navigation bridge.

## Not verified in this environment

- Full Chromium integration: the environment does not have the Playwright package installed, so Bridge tests use the proxy fallback and log `playwright_not_installed`.
- Real external navigation: DNS resolution for `example.com` is unavailable in this environment.
- Docker image build and runtime: Docker CLI is not installed here.
- Real SoloHost RAM/performance with 8–12 live pages was not measured. The default cap matches the existing 12-tab UI for correctness, but Pi deployments with low RAM may need lower, consistently configured caps.

The changes are syntax-checked and covered by regression tests, but the remaining items require validation on the actual SoloHost Docker runtime.
