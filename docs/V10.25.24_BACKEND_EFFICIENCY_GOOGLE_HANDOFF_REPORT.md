# SoloHost Browser v10.25.24 — Backend Efficiency & Google Sign-in Report

## Executive summary

The website engine remains a live Chromium session, not a crawler that repeatedly downloads a URL and rebuilds a page from scratch. Navigation runs through `playwrightEngine.navigate()`, which reuses the existing page when the normalized URL is unchanged. The SoloHost viewport displays a sanitized DOM snapshot of that live page. The important cost was repeated full DOM serialization after input/change/scroll events and eager activation of lazy images across the entire page.

Version 10.25.24 reduces that unnecessary work without changing the basic live-page + DOM-snapshot architecture.

## Completed changes

### 1. Avoid redundant snapshot work

- Added a short 160 ms snapshot cache and in-flight promise coalescing in `lib/engine/playwright-engine.js`.
- Navigation and non-scroll interactions invalidate the cache. Structural actions use a forced fresh snapshot.
- Input, change, and scroll events no longer clone/serialize the whole page on every event. The visible snapshot already reflects local input values; the backend still receives the event. A click/submit or actual URL change triggers the next snapshot.
- If an input/change handler changes the live page URL, the client refreshes the viewport snapshot; ordinary typing does not reload the viewport and therefore does not lose focus.
- Existing same-URL navigation reuse remains in place: `page.goto()` is not called again for the same normalized URL unless a caller explicitly asks for a forced reload.

### 2. Reduce image/network/memory pressure

- `getContent()` no longer changes every lazy image on the page to eager loading.
- Only images visible or near the viewport (up to 1.5 viewport heights/widths) have their lazy source activated. This avoids starting hundreds of image requests on long feeds when the user is only viewing the top of the page.
- The snapshot still contains the page DOM and keeps the existing in-frame lazy-media nudge; scrolling itself does not force a backend snapshot refresh.

### 3. User-Agent consistency

- Removed the hard-coded Chrome 131 User-Agent from the Chromium context and the separate noVNC login context. The engine now uses the installed Chromium's native User-Agent instead of advertising a potentially mismatched browser version.
- Mobile viewport, touch, and mobile-emulation flags remain enabled for mobile sessions.
- This is not a stealth or anti-detection feature. A native User-Agent cannot make a Playwright-controlled browser equivalent to a user-operated Chrome session, and it does not bypass website security policy.

### 4. Google sign-in: diagnosis and compliant handling

- Fixed the external handoff link to use the actual external target passed by the navigation handler, rather than potentially stale `state.url` from the previous page.
- Updated the notice to explain that Google blocks sign-in in many embedded/automation-controlled browser sessions and that the regular browser's cookies are isolated from SoloHost's backend Chromium profile.
- Google account pages are routed to the regular browser rather than repeatedly retrying login inside the automated snapshot browser. No cookie copying, fingerprint spoofing, CAPTCHA solving, or security bypass was added.

**Why Google rejects the login:** Google's documented supported-browser guidance says sign-in can be blocked when the browser is controlled by automation or embedded in another application. Its OAuth policy also prohibits directing Google OAuth requests to embedded user-agents under the app developer's control. See:

- https://support.google.com/accounts/answer/7675428?hl=en
- https://developers.google.com/identity/protocols/oauth2/policies
- https://developers.googleblog.com/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/

A generic browser cannot legitimately force Google to accept account login inside an automation-controlled backend. The regular-browser handoff is the safe fix for general website sign-in. Because the system browser and SoloHost's backend Chromium profile are separate, logging in through the handoff does not automatically copy that Google session into the backend. If SoloHost itself later needs Google account integration, it should use an official OAuth client and redirect flow with the app's own registered client/domain, not attempt to reuse the user's Google password or copy browser cookies.

## Files intentionally changed

- `lib/engine/playwright-engine.js`: short snapshot cache/coalescing, near-viewport lazy-image handling, native User-Agent, snapshot invalidation.
- `lib/engine/dom-bridge.js`: skip full snapshot after input/change/scroll; preserve scroll state; improve Google sign-in notice; explicit forced snapshot on structural actions.
- `public/app.js`: external link uses the actual handoff URL; input/change refreshes only if URL actually changed.
- `package.json`, runtime version strings, `README.md`, and versioned regression tests: version bumped to 10.25.24 and new test included.
- `test-v10.25.24-backend-efficiency.js`: regression coverage for snapshot optimization and Google handoff behavior.

No unrelated AI, memory, music/audio, tabs, bookmarks, persistent profiles, popup ownership, noVNC, SSRF protection, or existing security features were intentionally removed.

## Not verified in this environment

- The test environment reports `playwright_not_installed`, so a live Chromium end-to-end run was not possible here.
- External DNS was unavailable (`example.com` resolution failed), so real third-party website login and live navigation could not be tested.
- Actual SoloHost runtime RAM, load time, and multi-tab resource consumption were not measured. No performance numbers are claimed.
- Google may still reject an embedded or automation-controlled sign-in by policy; this version makes the handoff explicit and fixes the target URL, but does not promise Google login inside the backend Chromium session.
