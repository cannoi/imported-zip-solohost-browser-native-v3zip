# SoloHost Browser V10.9.7 — Login / YouTube / AI Agent Fix Report

## Source package examined

Input archive: `solohost-browser-v10.9.6-mount-resilient.zip`.

The archive contains a Node/Express SoloHost web app, Playwright Chromium backend, DOM Bridge viewport, legacy proxy fallback, backend AI agent, Universal AI, Feedback, Settings, Logs, Docker/Compose files and SoloHost `config_options.yml` files. The application is not a direct pixel-streaming Chromium window: it executes pages in headless Chromium and projects a sanitized DOM snapshot into the SoloHost UI.

## Root causes confirmed from source and log evidence

### 1. `agent_off` — confirmed fatal JavaScript syntax error

`lib/browser-agent.js` contained four multiline prompt strings whose closing quotes were missing. Requiring this module threw `SyntaxError: Invalid or unexpected token` at line 176. `server-app.js` catches that load failure and leaves both Browser Agent handlers on their fallback stubs, which return `agent_off`. `lib/backend-agent.js` also imports this module, so the backend task agent failed to load too.

**Fix:** repaired the prompt array into valid individual JavaScript strings. Added all-source JavaScript syntax validation and tests that load the real planner and backend agent.

### 2. Google sign-in rendered as a screenshot / external-open warning

`playwright-engine.js` captured screenshots whenever a page looked thin, was a sign-in URL, or had password/email fields. `dom-bridge.js` then chose a screenshot-only hybrid view for thin pages. The screenshot cannot receive focus, typing, click, or submit events, so the visible UI contradicted the existing backend input bridge.

**Fix:** screenshot fallback is no longer chosen for recognized authentication surfaces or sparse pages with interactive controls; when a sign-in/search DOM is available, the bridge keeps its sanitized controls and adds a clear credential-safety notice. Passwords and OTPs remain excluded from AI task inputs. Google may still require external sign-in if it enforces CAPTCHA or device verification.

### 3. YouTube video not playing

Two source-level blockers were found:
- The bridge viewport CSP declared `frame-src 'none'`, blocking the generated official YouTube embed player.
- The parent viewport iframe sandbox omitted `allow-scripts`, which also prevents scripts required by a nested player from running.
- In the HTML proxy, generic `specialShell()` intercepted concrete YouTube watch URLs before the titled player route could run.

**Fix:** CSP now allows only `www.youtube.com` and `www.youtube-nocookie.com` as child frame origins; the viewport sandbox permits nested scripts while the bridge document CSP still blocks scripts in the bridge document itself. Concrete watch URLs now reach the titled player handler before generic shells. The generated embed has a descriptive title and explicit referrer policy.

**Limit:** this does not add Widevine/DRM or guarantee every video can be embedded. Video owner restrictions, age gates, region restrictions, network policies and YouTube policy can still prevent playback.

### 4. Test suite failed before testing the app

The old `test.js`, `test-agent.js` and `test-backend-agent.js` expected API route wiring to be in `server.js`. In the supplied archive, `server.js` is a bootstrap and routes are mounted from `server-app.js`. The test suite therefore failed on stale source assumptions before exercising later tests.

**Fix:** tests now inspect both bootstrap and mounted app. Added `test-syntax.js` to parse all shipped `.js` files and added regressions for sign-in DOM retention, YouTube embed generation, frame policy and agent loading.

## Not verified / remaining work

- No Docker daemon or actual SoloHost runtime was available, so image build, container health, assigned SoloHost port mapping and runtime smoke test were **not** executed.
- No live Google sign-in, CAPTCHA, account verification or YouTube video playback was verified from this environment.
- The visible viewport is still a DOM projection rather than a full pixel-perfect browser surface. Canvas/WebGL-heavy pages, cross-origin widgets, some SPA controls, DRM and device-authenticated flows may remain limited.
- Firefox/WebKit are not yet wired as automatic fallback engines. Chromium is the current Playwright engine; WebKitGTK remains a separate optional legacy path.
- Persistent login profiles across app/tab restarts need a deliberate per-user profile lifecycle. The existing per-session contexts must not be changed to a shared global profile because that would mix users' cookies and credentials.
- No claim is made that every website or all Google/YouTube account flows work.

## Recommended next phase

1. Build the image with the exact Playwright base/package versions and run `/api/health` plus `/api/engine/status` inside SoloHost.
2. Test direct watch URLs with several public, embeddable videos and inspect browser console/network failures if any player remains blocked.
3. Test Google login DOM input end-to-end without sending credentials to the AI agent; document when external browser handoff is required.
4. Implement explicit per-user persistent browser profiles and session ownership before enabling long-lived sign-in.
5. Add Firefox/WebKit routing only after Chromium telemetry identifies reproducible engine-specific compatibility failures.
