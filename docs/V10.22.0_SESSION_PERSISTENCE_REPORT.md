# SoloHost Browser v10.22.0 — Session Persistence Hardening

## Findings
- The app already used Playwright browser contexts and saved `context.storageState()` snapshots under `/app/data/browser-state`, with private directories/files, atomic replacement and per-profile hashed filenames.
- Before this update, the snapshot omitted IndexedDB and was mainly saved on navigation, selected interactions and session close. Some modern sites update authentication state asynchronously in IndexedDB after the navigation event.
- The server fallback profile key used the client IP when the browser did not provide a profile ID, which could silently switch the persisted state after a network change.
- The app's user-facing browser remains a sanitized DOM Bridge snapshot, not a direct pixel stream from the Chromium window.

## Implemented
- Updated Playwright and the official Playwright Docker base image together to 1.51.1. This version supports `storageState({ indexedDB: true })`.
- Save cookies, localStorage and IndexedDB where supported. Existing state files remain loadable; the save path falls back to the older no-option API if the runtime does not support the option.
- Added a low-frequency, unref'ed autosave and page-load save so asynchronous login callbacks have more chances to persist. Existing saves on navigation, interaction and close remain. Private sessions do not write persistent state.
- Removed IP-based persistent identity. Explicit stable profile IDs remain isolated and persist across client IP changes; a missing/invalid profile ID receives a random isolated, non-persistent identity to avoid sharing cookies across clients. Private sessions remain isolated and non-persistent.
- Kept restricted file/directory permissions and atomic writes. No endpoint exposes cookies or storage JSON.

## Not implemented / limitations
- No attempt was added to defeat Cloudflare, DataDome, Akamai, CAPTCHA, or MFA controls. Navigator/fingerprint spoofing, TLS/JA3/JA4 impersonation and rotating-proxy evasion are not expanded. Legitimate site challenges remain user-completed.
- noVNC/Xvfb human takeover was not added. It requires a separately secured interactive desktop service and network exposure policy; adding it casually to the current static UI would enlarge the attack surface. Existing Bridge interaction and the official external-browser handoff remain the supported fallback.
- Playwright storageState does not guarantee every authentication mechanism is portable: sessionStorage, service-worker state, device-bound credentials, hardware-backed passkeys, and some provider-specific tokens may not be restored. Some services intentionally expire sessions.
- The visible app is still a DOM snapshot bridge, not a native Chromium pixel surface; this change improves persistence, not visual fidelity.
- Live SoloHost/container end-to-end sign-in and IndexedDB restoration still require validation in the deployment environment.

## Security notes
- Treat `/app/data/browser-state/*.json` as secrets: these files can contain authentication cookies. Keep the volume private, restrict backups, and never publish them.
- For shared deployments, configure SoloHost app access authentication and isolate users with separate profile IDs. Clients must send their stable profile ID to receive persistence. Missing IDs intentionally use isolated non-persistent sessions rather than risking cross-user credential sharing.
